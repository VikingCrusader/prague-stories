# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Backend (run from server/)
npm run dev          # nodemon on port 5000
npm run start        # production start
npm test              # Jest unit + controller integration tests (mongodb-memory-server)

# Frontend (run from client/)
npm run dev          # Vite dev server on port 5173
npm run build        # production build
npm test              # Jest unit/component tests
npm run test:e2e      # Playwright e2e (client/e2e/), mocks the backend via page.route

# Data scripts (run from server/)
node src/data/seedLocations.js    # upsert seeded location cards (idempotent)
node src/data/seedHistoryEvents.js # upsert History Timeline events (idempotent, $setOnInsert — see caveat below)
npm run export:locations          # export DB → static seed files
npm run sync:covers               # sync Cloudinary cover images to local

# Data scripts (run from client/)
npm run generate:covers           # rescan public/pixel-art/ → rebuild src/utils/coverManifest.json
```

There is no linter configured.

### Testing

- Server tests live in `server/__tests__/`. `rarityMap.test.js` and `gamification.test.js` are pure-function unit tests. `authController.test.js`, `locationController.test.js`, `checkinController.test.js`, `userController.test.js`, and `historyController.test.js` are integration tests that spin up an in-memory MongoDB (`mongodb-memory-server`) and drive the real Express app via `supertest` — they exercise actual Mongoose behavior (unique indexes, populate, lean) rather than mocking the models.
- `server/src/app.js` exports the Express app with no `listen()` call; `server/src/index.js` is the thin entry point that connects to Mongo and starts listening. Tests import `app.js` directly so they never need a real `MONGO_URI` or open a port.
- External calls (Cloudinary upload, Gemini description generation) are mocked in tests via `jest.unstable_mockModule`, not exercised for real.
- Client tests: `client/src/__tests__/` (Jest + RTL) for units/components, `client/e2e/` (Playwright) for full-page flows with the backend mocked via `page.route`.

## Architecture

This is a MERN monorepo (`client/` + `server/`) with no shared package between them.

### Backend (`server/src/`)

Express app with ES modules (`"type": "module"`). Entry point is `index.js` — mounts five route groups:

- `/api/auth` — register, login, `GET /me`
- `/api/locations` — CRUD + cover upload; GET routes use `optionalAuth` (populates `req.user` when a JWT is present but doesn't block unauthenticated requests); write routes use `protect`
- `/api/checkins` — check-in, history (no undo — check-ins are permanent once made)
- `/api/user` — XP progress, achievements
- `/api/history` — History Timeline events, read-only (`optionalAuth`, no write routes — content is hand-curated via a seed script, not user-submitted; see **History Timeline** below)

**Key patterns:**
- Location slugs are the canonical identifier throughout (not `_id`). All routes are `:slug`-based.
- `GET /api/locations` excludes the `description` field (too heavy for the grid). `GET /api/locations/:slug` includes it and triggers **lazy Gemini description generation** if any language is missing — it generates, saves to DB, and returns in the same request.
- GPS distance validation happens in the checkin controller. In `NODE_ENV=development` the check is skipped entirely so local testing works without being in Prague.
- Rarity and XP are coupled: `RARITY_XP` in `data/rarityMap.js` is the single source of truth. `createLocation` and `updateLocation` both call it to keep `xpReward` in sync with `rarity`.

**Models:**
- `Location` — `name` (EN display), `slug`, `localizedNames: { cz, zh }`, `labels[]`, `coordinates: { lat, lng }`, `description: { en, cz, zh }`, `rarity`, `xpReward`, `wikipediaUrl`, `coverImage`, `pixelArtKey`, `addedBy` (`null` = preset, `ObjectId` = user-added)
- `CheckIn` — `user`, `location` (ObjectId ref), `createdAt`
- `User` — `username`, `email`, `passwordHash`, `xp`, `achievements[]`
- `HistoryEvent` — `slug`, `era` (key into `data/historyEras.js`), `startYear` (numeric sort/timeline anchor, negative = BCE, not localized — a bare number reads fine in any language), `title`/`hookLine`/`summary`/`year: { en, cz, zh }` (`year` is the localized display string, e.g. `"935 (traditional date)"` / `"935 (tradičně uváděný rok)"` / `"935年（传统纪年）"`), `tone` (`humorous`/`serious`, stored but not yet read by the frontend), `quotes: [{ text: {en,cz,zh}, attribution: {en,cz,zh} }]` (primary-source quotes, referenced from inside `summary` via a `"[[quote:N]]"` marker on its own paragraph — see **Primary-source quotes** below), `relatedLandmarks: [{ slug, relation: { en, cz, zh } }]`, `wikipediaUrl`, `images` (array of static paths, e.g. `['/history/prehistory.webp']`), `imageCaptions: [{en,cz,zh}]` (optional small caption rendered under each image, matched to `images` by array index — an entry can be left `{}` for an image that doesn't need one). `summary` text may also contain inline `"[[link:slug]]display text[[/link]]"` markers (see **In-text cross-reference links** below) and `"[[b]]emphasized text[[/b]]"` markers for plain bold emphasis (see **In-text emphasis** below).

**Gamification** (`services/gamification.js`): `LEVELS` array and `ACHIEVEMENTS` array are the authoritative definitions for all level thresholds and achievement logic. `evaluateAchievements` runs on every check-in. Achievements fire once and are stored on the User document.

**Adding new locations (`data/seedLocations.js`):**
- Every entry needs a full `description: { en, cz, zh }` — all three languages, not just `en`.
- English description structure: an opening paragraph of ~50 words that introduces the location simply and humorously, followed by one or two main-text paragraphs with the substantive detail, followed by a final Bonus paragraph. CZ and ZH mirror this structure.
- Do not include Czech-name/place-name translations anywhere in the EN or ZH description text — in particular, no parenthetical Czech-translation note in the EN/ZH opening paragraph (e.g. no `Welcome to X (Český název)!` pattern).
- **History Timeline and Location descriptions are two separate content types — don't blur them (confirmed 2026-08-29).** A Location's `description` should not reference the History Timeline as a shared narrative the reader has supposedly already progressed through — no `"the Hussite general this project has already met never losing a single battle"`-style phrasing (`kost-castle`'s original draft), no `"this timeline has already told"` callbacks, no assuming the reader has read a specific History Timeline event. A Location card is meant to stand on its own; if a figure or event also appears on the History Timeline, that's a coincidence of subject matter, not a excuse to write as if the two features share one continuous story. (Some earlier entries — `bezdez-castle`, `zricenina-hradu-rotstejn`, `liberec` — already have this kind of cross-reference baked in from before this rule was confirmed; not retroactively fixed unless the user asks, but don't add more.)
- Don't add a `landmark` label to any new entry.
- `rarity`: `legend` is reserved for genuinely monumental/grand/massive buildings — usable for a new entry, not just the original preset landmarks, but sparingly. **Scope update (2026-08-22):** the original "never `legend` for new entries" rule was set when new locations were still Prague-only, where few buildings left to add were actually grand enough — now that new locations span all of Bohemia, a sufficiently monumental building anywhere in Bohemia (e.g. `zamek-hluboka-nad-vltavou`) can justify `legend` too. Default to `common`/`rare`/`superior`/`epic`/`mythic` for everything else. `xpReward` stays in sync automatically via `RARITY_XP` in `data/rarityMap.js`.
- `coordinates` are supplied by the user for each new location — don't look them up.
- **Scope rule for non-Prague locations (confirmed 2026-08-23): this app is "Prague Stories" — a city outside Prague only ever gets *one* Location card, treated as a single day-trip destination, not a second city to build out landmark-by-landmark.** Don't create a separate card for every notable sight within that same non-Prague city (e.g. a second statue, a second church) — fold anything else worth mentioning into that one city card's own description instead (as a sentence in its tourism paragraph, the way `ceske-budejovice`'s founder statue is handled) or into the History Timeline event's own prose, not as its own `relatedLandmarks` entry. The one standing exception is an out-of-town castle/monastery some distance from its nearest town (e.g. `bezdez-castle`, `zamek-hluboka-nad-vltavou`) — those can still get their own card even when a nearby town already has one. **Locations outside the Czech Republic never get a card at all** (e.g. Marchegg, Austria) — mention them only in running prose, never as a Location. **Second exception, confirmed 2026-08-24 (`vlassky-dvur`, `kostel-svate-barbory`, `kostnice-sedlec`, all in/around Kutná Hora):** the user's own stated two-part test for this specific exception — "库特纳霍拉是例外，因为离布拉格够近+旅游景点够硬，我才拆出来的" — a town has to clear **both** bars: (1) genuinely close enough to Prague to function as a satellite/day-trip town, not a distant second city, **and** (2) the individual sub-landmark itself has to be a serious, independently-major attraction in its own right (a real museum/monument people specifically travel to see — Kutná Hora's mint, cathedral, and ossuary all separately draw visitors), not just any notable building inside an already-carded town. Both conditions together, not either alone. This is a judgment call, not a blanket reopening of the one-card rule — flag it to the user rather than assuming it applies elsewhere, even for other Prague-adjacent towns (see `kutna-hora`'s own card, which still folds St. Barbara's Cathedral's basic facts into its own description even after St. Barbara's got a separate card, since the two serve different purposes: the town card's quick mention vs. the landmark card's full depth).
- **Third exception, confirmed 2026-08-24 (`olomouc`, and `brno`/`slavkov-u-brna` flagged for when they come up): a city can earn its own card purely on "just barely a Prague day trip + outsized standalone historical weight" grounds, without needing a Kutná Hora-style sub-landmark split.** User's own reasoning for Olomouc: close enough to still nominally count as a day trip from Prague, and it's the site of Wenceslas III's 1306 assassination (a major History Timeline event) plus its own separate deep bench of later history (Thirty Years' War Swedish occupation, the 1758 Prussian siege, 1848 imperial abdication). Brno was named in the same breath as a second, not-yet-built example, with Slavkov u Brna (Austerlitz, ~200km from Prague — well past the usual distance norms) flagged as a further one to revisit once the Napoleonic era is reached. **The house style for this exception is the opposite of the Kutná Hora pattern: write ONE long, rich card for the city itself (the `plzen`/`jihlava` template — intro paragraph, historical development, tourist landmarks folded into the same card's prose, closing bonus) rather than splitting named sub-landmarks into their own separate Location entries.** `olomouc`'s own card folds in its Holy Trinity Column, St. Wenceslas Cathedral, the Přemyslid bishop's palace, and its astronomical clock this way — none of those got (or should get) their own card.
- After writing the new entries, run `node src/data/seedLocations.js` (from `server/`) to upsert them into the database — just run it once the content is done, no need to ask first.

**History Timeline** (`models/HistoryEvent.js`, `data/historyEras.js`, `data/seedHistoryEvents.js`, `controllers/historyController.js`): a second, separate content type from Location — hand-curated historical events grouped into eight eras, browsable at `/history` on the frontend. `data/historyEras.js` is a static config (same reasoning as `RARITY_XP` in `rarityMap.js` — small, rarely-changing enum, not worth a DB collection) listing all eras with `key`, `order`, `themeClass`, `title: { en, cz, zh }`, `yearRange`, `tagline`, and `hasContent` (flip it manually once an era's events are seeded). As of 2026-08-23, `legends-origins`, `bohemian-duchy`, and `rise-of-a-kingdom` have real content; `kingdom-golden-age` and everything after are still placeholders. **Era 3/4 split (2026-08-23):** what used to be one era, `kingdom-golden-age` spanning 1199–1378, got split into two on the observation that "Bohemia's golden age" in actual historiography means Charles IV's reign specifically (1346–1378) — not the 148 years before it (Otakar II's rise-and-collapse, the Wenceslas II guardianship crisis, the 1306 Přemyslid extinction, John of Luxembourg's own reign as a rarely-in-Bohemia "wandering king" mortgaging crown lands rather than building anything lasting). `kingdom-golden-age` kept its key and now refers only to 1346–1378 (`hasContent` flipped back to `false` until real Charles IV events exist); the new era `rise-of-a-kingdom` covers 1199–1345 and inherited all ~32 previously-seeded events from the old single era (none of them post-date 1345). **`yearRange` corrected 2026-08-26 to 1199–1346:** the era's own content later grew to include John's 1346 death and Charles's 1346 King-of-the-Romans election, kept as `rise-of-a-kingdom`'s own closing bookend at the user's explicit direction rather than moved to `kingdom-golden-age` — the two eras now deliberately share 1346 as a boundary year, not by mistake. `GET /api/history` returns `{ eras, events }` in one payload — no list/detail split like `/api/locations`, since event copy is a few short hand-written sentences rather than a heavy lazily-generated description. Each event's `relatedLandmarks` stores bare Location slugs; the controller resolves them against the live `locations` collection in one batched query, enriches each with the full Location document (`-description` projection) plus a per-request `unlocked` flag computed the same way `getLocations` does it (via `CheckIn` lookup against `optionalAuth`'s `req.user`), and **silently drops any slug that doesn't resolve** rather than sending the client a dead link.

**Adding new history events (`data/seedHistoryEvents.js`):**
- Every event needs `title`, `hookLine` (one-sentence hook), and `summary` (2–3 sentences) in all three languages.
- **Voice**: default to wry, deadpan comic history-writing in all three languages — short punchy sentences, concrete specific details kept rather than smoothed into abstraction, and a dry closing line that reframes the facts as a joke. Model paragraph (`vysehrad-revival-1070`, the 1075 Langensalza / 1077 "Gebhard" aside): *"两人较劲用了不同的招——一个靠打仗立功，一个靠改名讨好皇帝——看来'想方设法气对方'才是这家人真正代代相传的东西。"* That's the target register for pre-modern content generally, not just this one event. Exception: modern-era atrocity/mass-death content (e.g. Lidice) stays solemn — same format, drop the jokes, not a Lidice-only rule. **Broader 20th-century pullback (confirmed 2026-08-24):** once content reaches the eras `brief-independence` (1918–1938), `nazi-nightmare` (1938–1945), and `cold-war-sorrow` (1946–1992) — see `data/historyEras.js` — default to a more restrained, measured voice generally, not just for individual atrocity-tagged events within them. Dry irony and understatement can still land (e.g. an era tagline noting Czechoslovakia's allies "hand it over to appease the neighbor next door"), but drop the punchy joke-closer structure that defines the earlier-era default, especially for anything touching occupation, violence, or repression directly. The material carries more sustained weight than earlier eras; the wit shouldn't be the default assumption that then gets card-by-card overridden.
- **Dash frequency (confirmed 2026-08-25):** em-dashes (`—`) had crept into overuse across all three languages, and the density itself makes sentences feel long and hard to read — pull back the frequency in new History Timeline prose, EN/CZ/ZH alike. Prefer a plain comma, a period and a new sentence, a colon where the aside is doing real explanatory work, or parentheses for a genuine aside/qualifier. **Not a ban** — the user confirmed explicitly ("也不是完全不能用破折号，但是要在不得不用的时候才用"): treat it as a last resort, reached for only when none of those alternatives actually works, not as one option among several to pick freely. This is a general house-style tightening, not specific to one language (compare [[feedback_natural_sentence_style]], which flagged the same tic as a ZH-specific "AI tell" — that observation still stands, but the fix now applies everywhere).
- **Shorter paragraphs** (confirmed 2026-10-07, after the user split `two-kings-1438`'s opening paragraph twice and asked for clearer paragraphing from now on): in `summary`, give each idea or story step its own paragraph (the problem, the cause, the decision, the action) instead of packing several beats into one block. A paragraph of more than about 4–5 sentences, or one that changes topic partway, should usually be split. Use the same breaks in EN/CZ/ZH.
- **Avoid the "this timeline" self-reference** (confirmed 2026-08-30, user said it reads badly and explicitly dislikes it): don't write card copy that breaks the fourth wall to talk about "this timeline" as a narrating entity — "this timeline already covered...", "这条时间线已经讲过...", "tahle časová osa už..." — even though this exact device had been in near-constant use across the whole file before this date (roughly 70–80 occurrences at the time it was flagged). Prefer a [[link:slug]] cross-reference (see below) when the callback target has its own card, or just rephrase the callback to an in-story actor instead of the meta-narrator — e.g. "Charles's own court had already worn out the story it was so eager to spread" rather than "this timeline has already told the story Charles's own court was so eager to spread." This is confirmed as a going-forward default for all new/edited copy; the large stock of already-shipped cards using the old device was NOT swept retroactively as part of this fix — only ask about a full retroactive pass if the user raises it, don't assume it's wanted.
- **Vary the forward-hook closer** (confirmed 2026-08-25): a card that deliberately doesn't finish its own story (leaving the actual next event for its own card) needs some closing line gesturing at what's coming, but "接下来发生的事，是另一个故事了" ("What came next is its own story") had become a reflexive default across the Rise-of-a-Kingdom arc — used on `crowned-twice-1307`, `seven-kings-then-none-1306`, `thoroughly-incompetent-king-1307`, `the-fleeing-princess-1310`, and others in a row. Don't lean on this one stock phrase every time. Vary the construction: name what's coming without narrating it ("what he did with it is its own story"), end on an image or irony instead of a meta-statement about "the story," pose it as an open question, or just stop cold on the last concrete fact and trust the reader to feel the cliffhanger without a signposting sentence at all. The underlying job (close this card without spoiling the next one) stays the same; the sentence doing that job shouldn't read identically card after card.
- **Primary-source quotes** (`quotes: [{ text: {en,cz,zh}, attribution: {en,cz,zh} }]`, added 2026-08-24): when `summary` needs to quote a chronicle or historian directly (the Zbraslav Chronicle, Palacký, Henry of Heimburg, etc.), don't just embed the quote inline as quoted prose inside a regular paragraph — pull it into its own `quotes[]` entry and drop a `"[[quote:N]]"` marker on its own line (surrounded by blank lines like any other paragraph break) at the point in `summary` where it should appear. **Proactively suggest one, don't wait to be handed the quote text** — when researching an event and a genuine primary-source line or a notable historian's own verdict turns up (in a chronicle, in a WebSearch result, anywhere), pull it into this format on your own initiative, the same way background-card and territory-map opportunities already get flagged unprompted elsewhere in this doc. **This means actively searching for one, not just noticing if one happens to surface** (confirmed 2026-08-25): whenever the user hasn't supplied chronicle text themselves, spend a WebSearch pass or two specifically looking for a primary-source line before finishing the card — if a first search comes up empty, a second, differently-worded pass is worth trying before concluding there's nothing (a real case: the first search for Elizabeth's 1310 escape in `the-fleeing-princess-1310` missed the actual chronicle passage entirely; a second, differently-phrased search found it, and it turned out more accurate than the modern-secondary-source detail already drafted into the prose). If a proper search genuinely turns up nothing quotable, that's fine — don't force a weak or tangential quote in just to have one. `HistoryEventSection.jsx` swaps that marker for a distinct blockquote — bordered box, large decorative quotation marks, italic text, right-aligned "— Source" attribution — instead of a plain `<p>`. Every inline quote that existed in the Rise-of-a-Kingdom arc as of 2026-08-24 (the Palacký quote, the "divine vengeance" Zbraslav quote, Henry of Heimburg's famine account, the Continuator of Cosmas welcome-scene quote, the Zbraslav "pleased the Bohemian king" line) has since been retroactively converted to this format at the user's request — this is now the standing convention for all quotes, not just new ones. **Gotcha when converting an inline quote:** check whether the original prose continued in the same paragraph right after the closing quote mark (no blank line) — if so, the marker needs an explicit blank line inserted after it too, or the marker paragraph ends up with trailing text glued onto it and fails the `^\[\[quote:(\d+)\]\]$` match (rendering as a broken visible-marker plain paragraph instead of a blockquote). `node --check` won't catch this; only visually re-checking each `[[quote:N]]` occurrence's surrounding context will.
- **External video/film references** (`referenceMaps` — originally map-only, later reused for this — see "Content gotchas and lessons" below — confirmed 2026-09-02): whenever researching an event turns up a real film or documentary clip dramatizing it (a period film, a museum/documentary excerpt), don't just let it go unmentioned — proactively surface it via a `referenceMaps` entry (`label` = the year, `description` = a one-line note on what the clip shows, `url` = the link), the same unprompted-suggestion instinct already applied to primary-source quotes, background cards, and territory maps elsewhere in this doc. First used on `the-first-defenestration-1419` (a scene from the 1955 Czechoslovak film *Jan Žižka*, supplied by the user). **Extended 2026-10-08 to famous artworks** (user's explicit praise and request): a well-known painting of the scene (e.g. a Mucha *Slav Epic* canvas, a 19th-century history painting) gets the same treatment, with `label` = the year it was painted and `url` = a museum/foundation page. First used on `the-chalice-and-the-pope-1462` (Mucha's *The Hussite King Jiří of Poděbrady*, 1923). A one-line mention in the prose that the artist painted this very scene works well alongside it. This is a "when you happen to find one" convention, not a mandate to go WebSearching specifically for film adaptations the way the primary-source-quote rule mandates searching for chronicle lines — a good clip is a bonus if it surfaces naturally, not a required search pass.
- **Background-knowledge cards** (`cardType: 'background'`, default is `'event'`): a non-dated explainer aside slotted into the feed at a specific point, for context a reader needs right there but that isn't itself a dated happening — e.g. `bohemia-not-one-city-1101`, inserted between `duke-go-round-1092` and `battle-of-chlumec-1126` to explain that 11th–12th-century Bohemia had several rival power centers (Prague Castle, Vyšehrad, Olomouc/Brno/Znojmo in Moravia, plus assorted local strongholds) rather than one obvious capital, right before a battle whose whole premise depends on that. Renders with a distinct dashed-gold-border look and a collapsible "Background" tag instead of the normal year/title-as-wiki-link header (see `HistoryEventSection.jsx`, `history.css`), and — critically — does **not** claim a year slot in `HistorySidebar`'s nav list (filtered out there and in `HistoryPage`'s scroll-spy) even though it still needs a `startYear` to sort into the right place in the feed. **Proactively suggest one** whenever a piece of genuinely useful but likely-obscure context comes up that doesn't fit inside any single dated event — a European-history convention worth spelling out, a neighboring country's or the wider Empire's political backdrop, a term or institution the reader needs defined before the next few events make sense. Don't wait to be asked; flag the opportunity the way the illustration-prompt and territory-map offers already get flagged (see the reminders elsewhere in this doc). **A background card can optionally carry an `image`** (rule relaxed 2026-09-02, see `the-five-roses-1394`'s Rožmberk coat-of-arms image below — a reference graphic the user supplied directly, not an AI-generated narrative illustration; captioned with its source per the user's own instruction). **A background card still never gets a non-empty `relatedLandmarks`, hard rule, no exception carved out for this** — it's supplementary knowledge only, not tied to a specific place. Confirmed explicitly by the user 2026-08-22 after an illustration and three landmark links were added to a background card and had to be stripped back out; revisited 2026-09-02 specifically on the image half of that rule (the user asked to add a real coat-of-arms image to `the-five-roses-1394` and, when told it broke the standing "no image" rule, chose to relax that half rather than treat this as a one-off exception — so future background cards may use an image too, judged the same way an event card's image would be, while the landmark-link half of the original rule stands unchanged). If a background card's topic naturally connects to a real landmark, hold that link for later and attach it to an actual dated event instead — don't attach it here. **Before writing one, also check whether the subject is going to become a protagonist of its own later** rather than staying background forever — e.g. the Vítkovci family (Rožmberk branch), name-dropped starting in Era 3's `iron-and-golden-king-1266` (Otakar founding `zlata-koruna`/`ceske-budejovice` to counterbalance them, confiscating `jindrichuv-hradec` from them) but deliberately *not* given a background card there (decided 2026-08-22): the Rožmberks become one of the most important noble families in later Bohemian history (Český Krumlov, active into the Hussite/Renaissance/Baroque eras, extinct 1611) and will very likely anchor their own dated event(s) later, where a proper introduction lands with more weight than a background aside now. A passing mention with no card is fine when this is true; don't spend a background card explaining someone who's about to get their own spotlight. **Update 2026-08-23: a short introductory background card now exists — `who-are-the-vitkovci-1276`**, inserted right after `enemies-on-every-side-1276`. Deliberately light: Vítek of Prčice's origins as a Přemyslid court official (cup-bearer 1165, seneschal 1169–75) turned South Bohemia/Austria-border landholder, his sons' split into the "Five Roses" branches (Krumlov, Rožmberk, Hradec, Landštejn, Stráž), and the general loyal-official-vs-rival tension — no mention of Záviš's later marriage to the widowed Kunigunda, his 1290 execution, or the Rožmberk branch's own later peak. **The deeper/fuller version is still deferred, standing reminder unchanged:** proactively flag it when the Rožmberk family specifically becomes a genuine protagonist of their own (Hussite-era Oldřich II in Era 5, first name-dropped in passing in `the-castle-nobody-came-to-save-1428` (Bechyně's lord had fallen out with him, so no relief came; Bechyně was a Lefl-of-Lažany castle, not a Rožmberk one), user said 2026-09-26 to wait for his proper entrance; **written 2026-09-29 as `who-was-oldrich-of-rozmberk-1434`, placed between `the-new-town-falls-1434` and `lipany-1434` (moved there 2026-10-07; the old timing note below is kept for context)** — originally: **timing confirmed 2026-09-29: write it at Lipany (1434)**, inserted just before Oldřich's own entrance with the lords' league, since through 1432 he is still only a one-line side figure. `the-five-roses-1394` already covers the five branches and Rožmberk absorbing Krumlov, so the new card should center on Oldřich II himself (Lipany, leadership of the Catholic party, Sigismund's chief ally, his forged imperial charters exposed only in the 19th century), with `trebon` as his seat; Vilém/Petr Vok and Český Krumlov later still) — the user asked to be told, not to have to ask again. **When that fuller card gets written, explicitly callback to where this thread started** — this short 1276 introduction, Záviš of Falkenstein's revolt, the Zlatá Koruna/České Budějovice foundations built specifically to contain this family, and the Jindřichův Hradec confiscation — don't just reintroduce the family cold; - **Era-overview cards** (`cardType: 'overview'`, added 2026-10-01): one per era, kept in `data/historyOverviews.js` (appended to `historyEvents` in `seedHistoryEvents.js`), slug `era-guide-<era-key>`, rendered by `HistoryOverviewCard.jsx` **in place of the era banner** (`HistoryEraDivider` is skipped for an era that opens with one). ### Frontend (`client/src/`)

React 18 + Vite SPA, deployed to Vercel. `vercel.json` lives in `client/` (not repo root) for SPA rewrite rules to apply.

**Routing** (`App.jsx`): All routes use `<ProtectedRoute guestOk>`. `ProtectedRoute` auto-calls `continueAsGuest()` via `useEffect` when a `guestOk` route is accessed without a user session — so unauthenticated visitors land in guest mode instead of being redirected to `/login`.

**State:**
- `AuthContext` — `user` (JWT-authenticated), `guest` (sessionStorage flag), `loading`. The `guest` flag controls UI differences (no collect button, no add location, guest-specific titles).
- `LanguageContext` — `lang` (`en`/`cz`/`zh`), `zhVariant` (`cn`/`tw`). `useT(key)` is the translation hook used everywhere. `useConvert()` applies opencc-js for Traditional Chinese conversion. Language persists in `localStorage`.

**API layer** (`services/api.js`): Single axios instance pointing to `localhost:5000` in dev and `prague-stories-api.onrender.com` in prod. JWT attached via request interceptor from `localStorage`.

**i18n:** All UI strings live in the `T` object in `LanguageContext.jsx`. Location display names follow the rule: `name` IS the English display field; generic terms (church, bridge) are translated, proper place/person names stay Czech. `localizedNames.cz` and `localizedNames.zh` are always set alongside any change to `name`.

**Location descriptions:** The `description` field on list endpoints is excluded. `LocationDetail` fetches the single-location endpoint to get the full object including descriptions. The lazy Gemini fallback on the server means descriptions populate on first open.

**Pixel art:** `utils/pixelArtMap.js` maps a `pixelArtKey`/label to an emoji, used as the last-resort fallback when no image loads at all. New cards get pixel art generated externally and dropped into `client/public/pixel-art/`; the map entry must be added manually.

**Cover images (local-first):** Location covers load from `client/public/pixel-art/` before ever touching Cloudinary, to keep image traffic off Cloudinary's quota — Cloudinary stays fully wired up as the fallback/upload backend, just not the default read path. `utils/coverManifest.json` (generated by `npm run generate:covers`, see Commands) maps `slug -> filename`, since files are named `<slug>.<ext>` or `<slug>-v<timestamp>.<ext>` (the versioned form is a cache-buster used both by regenerated external pixel art and by the dev-mode cover-upload endpoint, which also patches this manifest directly — see `updateCoverManifest` in `locationController.js`). `utils/localCover.js`'s `getLocalCoverPath(slug, cloudUrl)` does the lookup. `LocationCard`, `LocationDetail`, `MapPage`'s `SidebarDetail`, and `RandomDrawPage` each try, in order: local manifest match → `location.coverImage` (Cloudinary) → emoji fallback (`getArt`), and each passes `location.coverImage` as the second argument. **Local wins only while it is not older than the Cloudinary upload (changed 2026-09-21):** `getLocalCoverPath` compares the local filename's `-v<ms timestamp>` with the Cloudinary URL's `/upload/v<unix seconds>/` version, and when Cloudinary is newer it returns `null` so the caller falls through to Cloudinary. This is what makes a cover edited through the app's Edit button (which only touches Cloudinary + the DB in production — see `uploadCoverImage`) show up immediately, without a re-sync. Before this, local unconditionally won whenever a manifest entry existed, so in-app edits on any card with a synced local file were silently hidden (found when a batch of ~70 newly synced covers was committed). A local file with no `-v<timestamp>` in its name can't be compared and still always wins. Running `node src/data/syncCovers.js --refresh` (server/) then `npm run generate:covers` (client/) is still the way to pull Cloudinary's current image down to a local file (plain `node src/data/syncCovers.js`, no flag, only fills in slugs with no local file at all), and it does save Cloudinary traffic, since a synced file is newer than the upload it copied. After manually dropping new art into `pixel-art/` outside the upload endpoint, name it `<slug>-v<Date.now()>.webp` (a newer timestamp than the card's Cloudinary version, or the older Cloudinary cover will win) and rerun `npm run generate:covers` to pick it up. Covered by `src/__tests__/localCover.test.js`.
  - **Card thumbnails (2026-09-25):** originals are 1024–2048px (~150KB avg) but a grid card shows them at ~180–300 CSS px, which made mobile Explore slow. `npm run generate:covers` also writes a 480px-wide copy of every mapped cover to `public/pixel-art/thumbs/<same filename>` (via `sharp`, a client devDependency; existing thumbs are reused, orphaned ones deleted). Still **commit `thumbs/` alongside any new cover**, so the Vercel build only has to fill gaps. Because the build rewrites `coverManifest.json` from the files actually in the repo, a manifest entry for an uncommitted cover gets dropped on deploy instead of shipping a broken path. `LocationCard` loads `toThumbPath(localCover)` with `loading="lazy"`, falling back to the full-size local file if the thumb is missing (e.g. after a dev-mode upload before regenerating), and requests Cloudinary fallbacks through `toCloudThumbUrl` (`f_auto,q_auto,w_480`). **History Timeline** (`pages/HistoryPage.jsx`, `components/history/`, `styles/history.css`): `/history` renders every seeded event as a continuous vertical feed (`HistoryEventSection`, one per event) next to a sticky sidebar nav (`HistorySidebar`, grouped by era) — a normal scrollable page with persistent navigation, not a click-to-swap detail pane. `HistoryPage` tracks which sidebar entry is highlighted with a plain `scroll` listener (rAF-throttled) that finds the last section whose top has crossed a trigger line near the top of the viewport, not `IntersectionObserver` — an earlier version using the observer's `isIntersecting` entries picked the wrong "active" section when multiple sections partially overlapped the trigger band. Clicking a sidebar entry calls `scrollIntoView({ behavior: 'smooth' })` on the matching section.
  - **Sticky-positioning gotcha:** `.guide-page` (shared by `GuidePage`, `RandomDrawPage`, and `HistoryPage`) sets `overflow-y: auto` in `pixelart.css`. `#root` only has `min-height` (not `height`), so `.guide-page` never actually needs to scroll internally in practice — the real scrolling always happens at the window level — but the `overflow-y: auto` declaration alone still makes it a CSS "scroll container", which silently breaks `position: sticky` on any descendant (sticky computes against the nearest scroll container, and `.guide-page`'s own `scrollTop` never moves). `history.css` overrides it back to `overflow-y: visible`, scoped to `.history-page` only — don't remove that override, and don't add `position: sticky` inside `.guide-page` on another page without adding the same kind of scoped override.
  - **Sidebar z-index gotcha:** `.history-sidebar` sets `z-index: 10` — not decorative. `.loc-card` (used inside the feed's `.location-grid`) is `position: relative`, and both it and the sticky sidebar are otherwise `z-index: auto`, which stack by DOM order — the feed's cards come after the sidebar in the markup, so without an explicit z-index they paint *over* the sidebar as they scroll underneath it. Only visible on mobile (below the `820px` breakpoint), where `.history-layout` stacks to a column and the full-width sidebar and full-width feed share the same horizontal space — on desktop they sit side by side and never visually overlap, so this is easy to break without noticing on a desktop-only check. Don't remove the z-index.

Known, accepted trade-off: `.loc-card` no longer stretches to a uniform row height — it sits in a flex column now, so it sizes to its own content — meaning a little natural height variance between cards in the same row is expected and fine.
  - **Load performance (2026-09-25):** the feed renders all ~220 events at once, so four things keep it fast; don't remove them casually. (1) `GET /api/history?lang=<en|cz|zh>`: the client sends its language and the controller collapses every `{ en, cz, zh }` object to `{ [lang]: value || en }` (~1 MB → ~0.35 MB compressed), so switching language refetches. Without `lang` all languages come back. Landmarks carry only LocationCard's fields. (2) The controller caches the assembled payload in memory per language, checked on every request against the count plus newest `updatedAt` of `historyevents` and `locations`. A Mongoose `updateOne` sync (which bumps `updatedAt`) or a reseed shows up on the next request; a raw-driver write that doesn't touch `updatedAt` would not. (3) `.history-detail-panel` has `content-visibility: auto`, so off-screen panels skip layout. Before this, every CJK web-font slice finishing its download relaid the entire ~700k-px feed (1–2 s each, ~12 s to first paint on ZH).   - `unlocked` is force-set to `true` when a landmark is passed to `LocationCard` here — History isn't a discovery/gamification context (the event text already names the place), so Explore's "???" mystery treatment never applies on this page, regardless of the requester's real check-in state.

  - Sidebar era titles and left-border stripes are a flat `var(--gold)` everywhere, not the per-era `--era-accent` palette (`data/historyEras.js`'s `themeClass` → `.era-*` rules in `history.css`, which included a red and a purple) that used to color them.   - **Chinese pixel-font gotcha:** title-level classes here (`.history-event__title`, `.history-sidebar__era-title`) use `font-family: 'Press Start 2P'`, a Latin-only font. Without a matching entry in `global.css`'s `html[data-lang="zh"] ...` override block, Chinese text in that class silently falls through to a generic `monospace` fallback — same declared `font-size`, but visibly smaller/thinner than the Latin pixel font renders, reading as "this heading has no presence." When adding a *new* class with this font-family that Chinese users will see, add it to that override block (font-family swap + a larger zh-specific `font-size`) in the same pass, not as an afterthought.
  - **Mobile horizontal-overflow gotcha (fixed 2026-08, worth understanding if it comes back):** `.history-layout`'s base rule sets `align-items: flex-start` — correct on desktop, where the layout is row-direction and it lets the sidebar and feed size their *heights* independently. The `@media (max-width: 820px)` block switches `.history-layout` to `flex-direction: column` but originally never touched `align-items` — so on mobile the cross axis becomes horizontal, and `flex-start` there means children shrink-to-fit their own content's preferred width instead of stretching to the container's 100%. `.history-feed` has no width of its own, so it was sizing itself to the widest thing inside it (in practice the 2-column `.location-grid` in related-landmark sections, wanting ~630–680px) and dragging the *entire page*, navbar included, into horizontal scroll — not just the History section, even though only History-specific content was the actual cause. Fixed with `min-width: 0` on `.history-landmark-item`. ### Content gotchas and lessons

- **Vratislav vs Vladislav** — two different men a century apart: Vratislav II (r. 1061–92, first king 1085) vs Vladislaus II (r. 1140–73, second "borrowed crown" 1158). Established ZH: **弗拉季斯拉夫** = Vratislav, **弗拉迪斯拉夫** = Vladislav (季 vs 迪), checked against zh.wikipedia. Don't let a casually-typed draft suggestion "fix" this. No Bohemian Vratislav was ever crowned king except Vratislav II (`romansky-most-vysehrad` once said "Vratislav I"; fixed).
- **Verify large edits**: one large Edit silently turned straight quotes into curly quotes across a whole block (caught only by `node --check`). Re-run `node --check` after *every* large edit to `seedHistoryEvents.js`, not just before the DB sync.
- **Direct-DB sync writes**: a `troskovice` sync reported `modifiedCount: 1` and read back fine, then silently reverted (likely racing the un-guarded `seedLocations.js` upsert on import plus non-majority write concern). Fixed by guarding both seed scripts' upsert loops behind an `import.meta.url` entry-point check and by using `{ writeConcern: { w: 'majority', j: true } }`. For anything that matters, re-verify from a separate connection after a delay before saying it's live ([[feedback_db_sync_write_durability]]).
- **Live-DB drift** (standing gotcha): `hrad-trosky` is live as `legend`/100 XP while the seed says `epic`/50; `troskovice` is live `common`/10 while the seed says `rare`/20. Unreconciled, root cause unknown — only `description` was synced.
- **`referenceMaps` reuse**: its UI label was genericized to "More on this:" / "延伸资料：" / "Více k tomuto tématu:" (`history.referenceMapsLabel`), which also changed the 5 map-only cards. First non-map use: the 1955 film *Jan Žižka* clip on `the-first-defenestration-1419`.
- **Background-card feature** touches `HistoryEventSection.jsx`, `HistorySidebar.jsx`, `HistoryPage.jsx`, `history.css` and i18n keys `history.backgroundLabel`/`collapseCard`/`expandCard`; verify frontend changes with a full `vite build`, not just `node --check`.
- **`[[link:…]]` and `[[b]]` don't nest**: `INLINE_MARKUP_RE` in `HistoryEventSection.jsx` matches them in one flat pass, so a link inside a `[[b]]…[[/b]]` span renders as literal bracket text. Keep links outside bold sentences (caught before shipping on `undefeated-until-the-plague-1424`).
- **Inline `[[link:…]]` renders as `<span role="button" tabIndex={0}>`, not `<button>`** (a `<button>` is an atomic box and won't wrap mid-phrase). Link color: default `var(--text-primary)`, gold only on `:hover`; the underline marks it as a link.

### Illustration production rules

- **Base prompt template**: wide 16:9 (1024×576), a flat aged-tan parchment-textured frame band with Celtic-knot corner flourishes that fills the canvas edge to edge (not a "scroll" or sheet of paper; see "No white outer margin" below), painterly high-detail pixel art (not blocky 8-bit), one wide panoramic scene (no inset "vision-within-a-vision"), and a bottom caption plaque described as *"a simple, perfectly flat rectangular parchment-colored bar... straight parallel edges... not tilted or in perspective"* holding a **short** bold serif all-caps caption, rendered once with no repeated words. Offer 2–4 caption options instead of guessing.
- **Standard frame (user's call, 2026-10-07, applies to every new illustration):** the reference is `crowned-while-his-father-watched-1376.webp` ("SEVEN VOTES, NO CONTEST"): an aged parchment band of about 30px on a 1024px image (a thin dark outer edge, then tan parchment, then a dark inner line), slightly worn and scuffed, with Celtic-knot corner pieces and the plaque overlapping up into the artwork. "About half the usual width" was tried first and came out far too thin (`the-compacts-chased-down-1448`'s first image, about 8px on black), so describe it as *"a moderately narrow aged parchment frame band, slimmer than a heavy ornamental border but clearly visible and wide enough for the Celtic-knot corner pieces to sit comfortably on it; the parchment looks old, slightly worn and scuffed, with faint stains and a few small nicks along its outer edge"*, and keep the outer edge filling the canvas (any outside area pure black, never white). Images made before this date keep their old, inconsistent borders (measured 8 to 60+px, some torn-edged); the user decided to leave them until the second pass after the whole timeline is drafted. A batch re-frame in code (the 1376 frame as a template) was prototyped and parked: old corner knots overlap the artwork and would double up, and frame/plaque detection failed on 3 of 9 samples.
- **Frame constants (old wide frame, superseded by the narrow frame above)** (measured off `egerland-endgame-1322.webp`): border **48px on all four sides**; caption plaque **height 50px**, sitting on the bottom border band; plaque width = text + ~100px padding per side, max ~928px, min ~350px. **Leak gotcha:** literal numbers ("48px", "~928px", "~350px") have been rendered as visible text inside the artwork. Keep the numeric frame spec in its own block separate from the scene description, or describe sizing qualitatively ("sized generously to fit the caption with comfortable padding, neither cramped nor absurdly wide"), and always end with: *"do not render any sizing instructions, measurements, numbers, or annotations as visible text anywhere in the image — this describes the frame, it is not text to display."* Also state "no readable text/scale markers/annotations anywhere in the artwork."
- **No white gap**: state *"the illustrated scene must extend directly to the inner edge of the parchment border, with zero gap — no white, cream, or blank margin line of any kind between the border's inner edge and the artwork."*
- **No white outer margin** (2026-09-27): "parchment scroll border" makes the model draw a torn-edged sheet floating on a white canvas, leaving white around the ragged outer edge and in the corners. The page background is dark, so white there stands out badly. Describe the border as a flat frame band that fills the canvas to the outermost pixel, with straight, clean outer edges (no torn, ragged or curled edges, no drop shadow). Add a black fallback: *"if any area outside the frame is unavoidable, it must be solid pure black, never white or light grey."* Also avoid the word "scroll". The prompt alone doesn't reliably fix it, so run every generated image through `python client/scripts/fillMargins.py <in> <out.webp>` (native `E:\` paths): it floods from the image border through near-white pixels only and fills them with `--bg-card` (`#111428`, the `.history-detail-panel` background), so the margin disappears into the page. It also writes the WebP, so it replaces the Pillow conversion step below.
- **Caption text**: a dropped negation reads as a plausible sentence ("NOT EVEN CAESAR WROTE THIS" came back without "NOT") — double-check any caption built on a negation. `imageCaptions[i]` (the small line under the image) should describe the scene plainly, not echo the plaque text.
- **Character consistency**: write the full locked description word-for-word in every prompt — "the same character as before" fails (Wenceslas came back with a different face). When a locked-design figure is in a scene but *not* the foreground figure, say explicitly and by name that no other figure shares his distinguishing features (Žižka's eyepatch/fur hat/fur cloak bled onto the nearest figure once).
- **Architecture/setting anchors**: no Gothic spires before 1344; Prague skyline = red-tiled rooftops up the hill, Vltava in golden light, stone arch bridge, scaffolded St. Vitus silhouette on the castle hill. The user knowingly accepted a bridge in pre-1357 skylines (Charles Bridge didn't exist yet) — don't re-litigate; from 1357 on, bridge and cathedral can both be shown under construction with no hedging. When depicting the very first stone of the bridge, state that no completed multi-arch bridge may appear anywhere.
- **Battle prompts**: say explicitly that a routed army is fleeing *away* (it rendered as a second charging wave); Luxembourg arms are barry silver-and-blue with a red lion (it rendered a modern tricolor); a "blind" figure must have eyes closed/covered.
- **Hussite banners**: always a **yellow cup-shaped chalice on a red field** (Tábor's own, Žižka's included — the old red-field/white-chalice variant is retired). Describe the chalice as an actual cup-shaped icon; naming only the colors gives a plain red flag.
- **Early hand-cannons (1419–20)**: a short plain metal tube on a straight unshaped wooden pole, no stock/curved grip/trigger, must not resemble a musket; two men — one braces the pole rear against his chest/under an arm/against a wagon edge, the second touches a smoldering match-cord to a touch-hole near the rear. Fold this into one complete prompt rather than iterating in small amendments. Evolve the look as the wars progress.
- **Real-photo "artifact" frame**: a second, deterministic (Python/Pillow, not AI) treatment for genuine photographs/objects — dark museum-wall background with soft vignette, photo letterboxed inside a thin gold double-line frame with small gold diamond corners, brass-gradient caption plaque in Georgia Bold. Used for the 1997 100-koruna banknote on `father-of-the-fatherland-1378`. The original script lived in an old scratchpad; rebuild the logic in a fresh scratchpad file. Keep the Celtic-knot parchment style for all generated scenes.
- **Format**: if a generated image arrives as `.jpg`, convert with Python + Pillow (`Image.open(...).convert('RGB').save(path, 'WEBP', quality=90)`) — no `cwebp`/ImageMagick/ffmpeg on this machine; use native `E:\...` paths, not Git Bash paths. After adding an image, set `image` in `seedHistoryEvents.js` *and* live via `HistoryEvent.updateOne({ slug }, { $set: { image } })` (`$setOnInsert` won't touch seeded docs).
