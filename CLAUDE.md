# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Backend (run from server/)
npm run dev          # nodemon on port 5000
npm run start        # production start
npm test              # Jest unit + controller integration tests (mongodb-memory-server)

# Frontend (run from client/)
npm run dev          # Vite dev server on port 5173
npm run build        # production build
npm test              # Jest unit/component tests
npm run test:e2e      # Playwright e2e (client/e2e/), mocks the backend via page.route

# Data scripts (run from server/)
node src/data/seedLocations.js    # upsert seeded location cards (idempotent)
node src/data/seedHistoryEvents.js # upsert History Timeline events (idempotent, $setOnInsert — see caveat below)
npm run export:locations          # export DB → static seed files
npm run sync:covers               # sync Cloudinary cover images to local
npm run sync:expedition           # recompute rarity/XP of live cards (outside → expedition); --dry to preview

# Data scripts (run from client/)
npm run generate:covers           # rescan public/pixel-art/ → rebuild src/utils/coverManifest.json
```

There is no linter configured.

### Testing

- Server tests live in `server/__tests__/`. `rarityMap.test.js` and `gamification.test.js` are pure-function unit tests. `authController.test.js`, `locationController.test.js`, `checkinController.test.js`, `userController.test.js`, and `historyController.test.js` are integration tests that spin up an in-memory MongoDB (`mongodb-memory-server`) and drive the real Express app via `supertest` — they exercise actual Mongoose behavior (unique indexes, populate, lean) rather than mocking the models.
- `server/src/app.js` exports the Express app with no `listen()` call; `server/src/index.js` is the thin entry point that connects to Mongo and starts listening. Tests import `app.js` directly so they never need a real `MONGO_URI` or open a port.
- External calls (Cloudinary upload, Gemini description generation) are mocked in tests via `jest.unstable_mockModule`, not exercised for real.
- On the macOS 12 dev machine, the cached in-memory `mongod` 8.2 won't start (needs a newer libc++); run server tests with `MONGOMS_VERSION=7.0.14 npm test`.
- Client tests: `client/src/__tests__/` (Jest + RTL) for units/components, `client/e2e/` (Playwright) for full-page flows with the backend mocked via `page.route`.

## Architecture

This is a MERN monorepo (`client/` + `server/`) with no shared package between them.

### Backend (`server/src/`)

Express app with ES modules (`"type": "module"`). Entry point is `index.js` — mounts five route groups:

- `/api/auth` — register, login, `GET /me`
- `/api/locations` — CRUD + cover upload; GET routes use `optionalAuth` (populates `req.user` when a JWT is present but doesn't block unauthenticated requests); write routes use `protect`
- `/api/checkins` — check-in, history (no undo — check-ins are permanent once made)
- `/api/user` — XP progress, achievements
- `/api/history` — History Timeline events, read-only (`optionalAuth`, no write routes — content is hand-curated via a seed script, not user-submitted; see **History Timeline** below)

**Key patterns:**
- Location slugs are the canonical identifier throughout (not `_id`). All routes are `:slug`-based.
- `GET /api/locations` excludes the `description` field (too heavy for the grid). `GET /api/locations/:slug` includes it and triggers **lazy Gemini description generation** if any language is missing — it generates, saves to DB, and returns in the same request.
- **Stories are only for those who collected the card (user's rule, 2026-10-16):** for anyone who hasn't checked in there (and didn't add the card, `addedBy`), `GET /api/locations/:slug` cuts `description` to the preview on the server (`storyTeaser` in `locationController.js`: the first paragraph, or two when the story has more than 3 and the EN opening is 20 words or fewer) and sets `storyLocked: true`; the detail views show that as is and refetch the full story after a check-in. `PUT` refuses a `description` change (403) from such a user, and on a `storyLocked` card the Edit form hides the story fields and leaves `description` out of the save, so the button stays for everyone (the user uploads covers through it). On History, landmarks are shown as `unlocked` for display, so `LocationCard` gets `holdable={landmark.unlocked}` to keep the showcase (long press / double click, which shows the full story) to cards the user really collected.
- GPS distance validation happens in the checkin controller. In `NODE_ENV=development` the check is skipped entirely so local testing works without being in Prague.
- **Treasure Hunt (寻宝):** the only game on the `/treasure-hunt` page (`TreasureHuntPage.jsx`, `TreasureHuntPanel.jsx`; old `/random-draw` redirects there). **One hunt since 2026-10-29 (user's call):** the separate Clues and Hardcore modes (2026-10-12 / 2026-10-15) were merged, keeping what was tense in each and dropping what was dull or frustrating. Core rule: **walking earns clues for free, pressing the button and buying clues cost multiplier.** API routes and `User.randomDraw` keep their old "random draw" names (from the open draw, 明抽, removed 2026-10-12 as boring; a leftover `mode: 'open'` draw counts as no draw and pays no bonus). One hunt per 24h, login only (guests see the rules and a disabled start button). No re-roll (dropped in the merge), no time bonus (a 2-hour x1.5 was removed 2026-10-12 so a hard hunt doesn't feel rushed). Pool (`huntPoolMatch`): uncollected city cards (not `outside`) with a quarter, minus `HUNT_EXCLUDED_SLUGS` in `gamification.js` (bridges over the Vltava, Charles Bridge statues, the islands and what stands on them, the Old Town Weir, the Podbaba ferry: the river-side clue can't describe them, user's call 2026-10-15). The treasure is picked at least 4 km (`HUNT_MIN_START_M`) from where the player starts the hunt, so every hunt is a walk; with nothing that far left, any pool card will do (user's call, 2026-10-29). **A hunt can only be started inside Prague (2026-10-30, user's call):** `drawRandomLocation` needs a position (400 `positionRequired`) inside the city boundary (403 `outsidePrague`), checked by `utils/pragueBoundary.js` against `data/pragueBoundary.json` (the 22 správní obvody, written by `client/scripts/buildPragueAreas.mjs` next to the client's own copy); skipped in development like the check-in distance check; the page shows the reason under the start button. Location and coordinates never go to the client until found; the server computes every clue (`buildHuntClues` in `userController.js`) from the position the client reports (`GET /api/user/random-draw?lat&lng`, polled every 10 s), and that call also stores the clues walking brought.
  - **Clues (reworked 2026-10-31, user's call, for the thrill of a treasure slowly giving itself away; replaces the 2026-10-29/30 designs with planned, pre-checked label clues and random bought clues).** Nothing but the distance at the start. **Why attribute clues come late:** labels, rarity, quarter and district are filters on Explore and the map, where every locked card shows its labels and distance. Distance (`huntReading`): rounded to the whole km from 3 km out (5.8 and 6.4 km both "about 6 km", stated in the rules), to the half km from 3 km down to 1 km, then the bands `{ band: [500, 1000] }` "not far now", `{ band: [300, 500] }` "very close", and `{ within: 300 }` "right around you" (whole sentences in the panel). **Never "within 100 m" (the hit radius, dropped 2026-10-29):** with it a press could never miss. Hot and cold every ~100 m (`HUNT_TREND_STEP_M`, under 40 m = same) **only outside `HUNT_TREND_MAX_M` (500 m)**: inside it the clues are enough and a verdict every 100 m would point the way, which only a miss should do. **The clues come in a fixed order (`HUNT_CLUE_ORDER`): river bank (`side`, from the quarter via `LEFT_BANK_QUARTERS`: "castle side" / "Old Town side"), district, quarter, then the label or the rarity 50/50 (`HUNT_CLOSE_KEYS`; a label is any of the card's labels, each as likely, stored on the clue as `label`: the luck is deliberate, no pre-screening), then the other one.** Walking brings each for free at `HUNT_FREE_CLUE_AT` (3 km, 1 km, 500 m, 300 m; the last one is buy-only), pushed with `free: true` (doesn't count toward the multiplier), flashed once. **Buying (`POST /api/user/random-draw/clue`, `takeHuntClue`) gets the next clue in the order early, from anywhere; a clue already had is skipped when walking reaches its distance.** No bought direction any more: the direction only comes with a miss. The response carries `nextClue` (a key, or `rarityOrLabel` while that slot is undrawn) for the buy button and confirm, and `nextFree`. Hunts dealt before the rework (`firstClue`/`labelOrder` set) count the river side as had and an old `area` clue as district plus quarter (`cluesHad`); `planHuntClues`, `orderHuntLabels` and the label/quarter checks are gone. The XP figure shows only once the rarity is known.
  - **Presses and multiplier.** The button works anywhere (`POST /api/user/random-draw/guess`); within 100 m (`HIDDEN_DRAW_HIT_M`) it finds the card, and every press asks for confirmation. `HUNT_MULTIPLIERS = [10, 5, 3, 2, 1]` (2026-10-31): **a miss drops two rungs (10 → 3 → 1: without clues only two presses pay a bonus), a bought clue one rung.** 1x is the card's plain XP, the floor; presses are unlimited (user's call: no zero-XP outcome). A miss reports only its direction from the pressed spot, never a distance; misses never end the hunt, so a hunt only fails by timing out, then `lastHunt` reveals the answer and later check-ins are 1x. **Only a press on the Treasure Hunt page pays the multiplier (2026-10-30, user's call):** a normal check-in on the target pays the card's plain XP and ends the hunt unfound (`randomDraw.forfeited`; presses and clues 409), since otherwise a player could check in at every nearby candidate for free. Leftover `{ skipped: true }` misses from the old clue mode count as a clue (`huntStepOf`, `huntMissCount`). The rules' clue table (`HuntClueTable` in `TreasureHuntPage.jsx`) hard-codes the clue order and free distances and must mirror the server constants. On phones the page's challenge box (`.guide-challenge--fold`) has a smaller font and a show less / more toggle that folds it to three lines; it starts open on a first visit and folding is remembered in `localStorage.huntChallengeFolded`; desktop is unchanged (user's calls, 2026-10-31). **Design intent:** 10x should come from walking all the way there and hitting on the first press; a long walk is the point, don't tune it toward quick or easy.
  - **Storage and display.** The hitting press is `CheckIn.guessAttempt` (and the XP paid `xpEarned`); old hardcore finds still carry `CheckIn.huntMode: 'hardcore'` and their detail line still says "硬核寻宝所得" (`detail.huntFindHardcore`); new finds say "寻宝所得，N次猜中 +Y XP" (`detail.huntFind`) in `LocationDetail` and the `MapPage` sidebar. Cards carry no hunt badge (removed 2026-10-13). Sounds (`utils/sound.js`, synthesized with Web Audio like the other app sounds, no audio files): `playShuffleSound` on start (timed to the shuffle animation's keyframes), `playClueSound` on a clue taken, `playMissSound` on a miss, `playHuntWinSound` on a find; after a find the XP update (and any level-up modal with its own fanfare) waits `HUNT_WIN_SOUND_MS` so the two don't overlap. Each tap handler calls `unlockAudio()` first, since iOS keeps an AudioContext started after an await silent. Starting a hunt plays `DeckShuffle.jsx` (2.3 s, CSS `deck-*` keyframes; `SHUFFLE_MS` must match; skipped under `prefers-reduced-motion`). The old `User.hardcoreDraw` is out of the schema; `npm run purge:hunt-positions` (server/) unsets leftover ones along with ended hunts' `trendRef`.
- Rarity and XP are coupled: `RARITY_XP` in `data/rarityMap.js` is the single source of truth for the six city tiers. A `pre('validate')` hook on `Location` (`resolveRarity`) keeps `rarity`/`xpReward` in step with labels and coordinates on every save, and `seedLocations.js` applies the same function before its upsert.
- **Expedition (远征 / Výprava, 2026-10-16):** every `outside` card has the seventh rarity `expedition`, never a city tier (a card that loses `outside` drops to `common`). Its XP comes from the straight-line distance to Charles Bridge: under 25 km 60, 25–50 km 120, 50–100 km 180, 100–150 km 240, 150 km and over 300 (`EXPEDITION_XP_STEPS`), never below 60. `EXPEDITION_XP_OVERRIDES` moves cards up (famous/grand: Karlštejn 240, Krumlov and Hluboká 300, …) or down (small sights bundled with a bigger nearby card: the Trosky/KCD ponds and villages, Tetín's small cards, two Kutná Hora cards, …); all user-approved, and only one of the five steps is allowed. After changing either table, run `npm run sync:expedition`. Applies to check-ins from 2026-10-16 on; past check-ins keep the XP they paid, and level thresholds were deliberately left unchanged. Frontend: always a silver frame (`pixelart.css`, `data-rarity="expedition"`), with the stone in the four edge settings picked from `xpReward` (`expeditionGem` in `utils/rarity.js`, `data-gem` on `LocationCard`): 60 bronze rivet, 120 ruby, 180 and up a deep-blue diamond (the only animated one, and its frame is fancier: mythic's fuller corner flourish, a silver glint round the ornaments, a blue outer glow; obsidian and emerald for 120/180 and ruby for 240 were the first design, changed the same day at the user's call so more cards carry diamonds). The card face just says 远征 / Expedition / Výprava like any tier. The rarity filter on Explore and Map only offers Expedition with "Show all" (and drops it when switching back to City only). **Rarity filter is single-select (2026-10-16)** on Explore and Map: picking another rarity replaces the active one, picking it again clears it. On Explore the picked rarity's one-line description shows under the title / "where you are" line (`.explore-rarity-blurb`); that slot shows one thing at a time, rarity description first, then the area blurb, then the My Collections hint. While a rarity is picked, the intro line (city / Show all blurb) is not shown either; the "where you are" badge stays. The descriptions live in `utils/rarityBlurbs.js` (`RARITY_BLURB`), which the Guide's rarity list is also built from, so edit them there, not in `GuidePage.jsx`.

**Adding new locations (`data/seedLocations.js`):**
- Every entry needs a full `description: { en, cz, zh }` — all three languages, not just `en`.
- English description structure: an opening paragraph of ~50 words that introduces the location simply and humorously, followed by one or two main-text paragraphs with the substantive detail, followed by a final Bonus paragraph. CZ and ZH mirror this structure.
- Do not include Czech-name/place-name translations anywhere in the EN or ZH description text — in particular, no parenthetical Czech-translation note in the EN/ZH opening paragraph (e.g. no `Welcome to X (Český název)!` pattern).
- **History Timeline and Location descriptions are two separate content types — don't blur them (confirmed 2026-08-29).** A Location's `description` should not reference the History Timeline as a shared narrative the reader has supposedly already progressed through — no `"the Hussite general this project has already met never losing a single battle"`-style phrasing (`kost-castle`'s original draft), no `"this timeline has already told"` callbacks, no assuming the reader has read a specific History Timeline event. A Location card is meant to stand on its own; if a figure or event also appears on the History Timeline, that's a coincidence of subject matter, not a excuse to write as if the two features share one continuous story. (Some earlier entries — `bezdez-castle`, `zricenina-hradu-rotstejn`, `liberec` — already have this kind of cross-reference baked in from before this rule was confirmed; not retroactively fixed unless the user asks, but don't add more.)
- Don't add a `landmark` label to any new entry.
- `rarity` (city cards only; an `outside` card becomes `expedition` automatically, whatever the seed entry says): `legend` is reserved for genuinely monumental/grand/massive buildings — usable for a new entry, not just the original preset landmarks, but sparingly. **Scope update (2026-08-22):** the original "never `legend` for new entries" rule was set when new locations were still Prague-only, where few buildings left to add were actually grand enough — now that new locations span all of Bohemia, a sufficiently monumental building anywhere in Bohemia (e.g. `zamek-hluboka-nad-vltavou`) can justify `legend` too. Default to `common`/`rare`/`superior`/`epic`/`mythic` for everything else. `xpReward` stays in sync automatically via `RARITY_XP` in `data/rarityMap.js`.
- `coordinates` are supplied by the user for each new location — don't look them up.
- **City boundary and district (2026-10-11):** a location outside Prague's administrative boundary (OSM relation 435514) gets the label `outside` (布拉格以外), appended last so the primary label stays first; Explore and the Map sidebar hide those cards by default ("City only" toggle, `ScopeToggle.jsx`). A location inside the boundary instead gets `district: 'Praha N'`, its správní obvod (1–22: each Praha N městská část plus its smaller neighbours, per cs.wikipedia "Členění Prahy"), computed by point-in-polygon against the 57 OSM městská část boundaries (admin_level 9), and `quarter`, its katastrální území (112 of them, the historical towns/villages: `'Staré Město'`, `'Smíchov'`, … — official Czech name; EN/ZH display names in `client/src/utils/pragueQuarters.js`). Both come from ČÚZK's RÚIAN service (`ags.cuzk.gov.cz/arcgis/rest/services/RUIAN/Prohlizeci_sluzba_nad_daty_RUIAN/MapServer`, layer 7 KatastralniUzemi with `obec=554782`, layer 10 SpravniObvodVHlavnimMestePraze), which agreed 100% with the OSM-based districts. `DistrictLine.jsx` shows quarter + district (or "Outside Prague") as their own pill row under the descriptive labels in both detail views. The four Prague poles stay inside, no `outside` label.
- **Scope rule for non-Prague locations (confirmed 2026-08-23): this app is "Prague Stories" — a city outside Prague only ever gets *one* Location card, treated as a single day-trip destination, not a second city to build out landmark-by-landmark.** Don't create a separate card for every notable sight within that same non-Prague city (e.g. a second statue, a second church) — fold anything else worth mentioning into that one city card's own description instead (as a sentence in its tourism paragraph, the way `ceske-budejovice`'s founder statue is handled) or into the History Timeline event's own prose, not as its own `relatedLandmarks` entry. The one standing exception is an out-of-town castle/monastery some distance from its nearest town (e.g. `bezdez-castle`, `zamek-hluboka-nad-vltavou`) — those can still get their own card even when a nearby town already has one. **Locations outside the Czech Republic never get a card at all** (e.g. Marchegg, Austria) — mention them only in running prose, never as a Location. **Second exception, confirmed 2026-08-24 (`vlassky-dvur`, `kostel-svate-barbory`, `kostnice-sedlec`, all in/around Kutná Hora):** the user's own stated two-part test for this specific exception — "库特纳霍拉是例外，因为离布拉格够近+旅游景点够硬，我才拆出来的" — a town has to clear **both** bars: (1) genuinely close enough to Prague to function as a satellite/day-trip town, not a distant second city, **and** (2) the individual sub-landmark itself has to be a serious, independently-major attraction in its own right (a real museum/monument people specifically travel to see — Kutná Hora's mint, cathedral, and ossuary all separately draw visitors), not just any notable building inside an already-carded town. Both conditions together, not either alone. This is a judgment call, not a blanket reopening of the one-card rule — flag it to the user rather than assuming it applies elsewhere, even for other Prague-adjacent towns (see `kutna-hora`'s own card, which still folds St. Barbara's Cathedral's basic facts into its own description even after St. Barbara's got a separate card, since the two serve different purposes: the town card's quick mention vs. the landmark card's full depth).
- **Third exception, confirmed 2026-08-24 (`olomouc`, and `brno`/`slavkov-u-brna` flagged for when they come up): a city can earn its own card purely on "just barely a Prague day trip + outsized standalone historical weight" grounds, without needing a Kutná Hora-style sub-landmark split.** User's own reasoning for Olomouc: close enough to still nominally count as a day trip from Prague, and it's the site of Wenceslas III's 1306 assassination (a major History Timeline event) plus its own separate deep bench of later history (Thirty Years' War Swedish occupation, the 1758 Prussian siege, 1848 imperial abdication). Brno was named in the same breath as a second, not-yet-built example, with Slavkov u Brna (Austerlitz, ~200km from Prague — well past the usual distance norms) flagged as a further one to revisit once the Napoleonic era is reached. **The house style for this exception is the opposite of the Kutná Hora pattern: write ONE long, rich card for the city itself (the `plzen`/`jihlava` template — intro paragraph, historical development, tourist landmarks folded into the same card's prose, closing bonus) rather than splitting named sub-landmarks into their own separate Location entries.** `olomouc`'s own card folds in its Holy Trinity Column, St. Wenceslas Cathedral, the Přemyslid bishop's palace, and its astronomical clock this way — none of those got (or should get) their own card.
- After writing the new entries, run `node src/data/seedLocations.js` (from `server/`) to upsert them into the database — just run it once the content is done, no need to ask first.

**History Timeline** (`models/HistoryEvent.js`, `data/historyEras.js`, `data/seedHistoryEvents.js`, `controllers/historyController.js`): a second, separate content type from Location — hand-curated historical events grouped into eight eras, browsable at `/history` on the frontend. `data/historyEras.js` is a static config (same reasoning as `RARITY_XP` in `rarityMap.js` — small, rarely-changing enum, not worth a DB collection) listing all eras with `key`, `order`, `themeClass`, `title: { en, cz, zh }`, `yearRange`, `tagline`, and `hasContent` (flip it manually once an era's events are seeded). As of 2026-08-23, `legends-origins`, `bohemian-duchy`, and `rise-of-a-kingdom` have real content; `kingdom-golden-age` and everything after are still placeholders. **Era 3/4 split (2026-08-23):** what used to be one era, `kingdom-golden-age` spanning 1199–1378, got split into two on the observation that "Bohemia's golden age" in actual historiography means Charles IV's reign specifically (1346–1378) — not the 148 years before it (Otakar II's rise-and-collapse, the Wenceslas II guardianship crisis, the 1306 Přemyslid extinction, John of Luxembourg's own reign as a rarely-in-Bohemia "wandering king" mortgaging crown lands rather than building anything lasting). `kingdom-golden-age` kept its key and now refers only to 1346–1378 (`hasContent` flipped back to `false` until real Charles IV events exist); the new era `rise-of-a-kingdom` covers 1199–1345 and inherited all ~32 previously-seeded events from the old single era (none of them post-date 1345). **`yearRange` corrected 2026-08-26 to 1199–1346:** the era's own content later grew to include John's 1346 death and Charles's 1346 King-of-the-Romans election, kept as `rise-of-a-kingdom`'s own closing bookend at the user's explicit direction rather than moved to `kingdom-golden-age` — the two eras now deliberately share 1346 as a boundary year, not by mistake. `GET /api/history` returns `{ eras, events }` in one payload — no list/detail split like `/api/locations`, since event copy is a few short hand-written sentences rather than a heavy lazily-generated description. Each event's `relatedLandmarks` stores bare Location slugs; the controller resolves them against the live `locations` collection in one batched query, enriches each with the full Location document (`-description` projection) plus a per-request `unlocked` flag computed the same way `getLocations` does it (via `CheckIn` lookup against `optionalAuth`'s `req.user`), and **silently drops any slug that doesn't resolve** rather than sending the client a dead link.

**Adding new history events (`data/seedHistoryEvents.js`):**
- Every event needs `title`, `hookLine` (one-sentence hook), and `summary` (2–3 sentences) in all three languages.
- **Voice**: default to wry, deadpan comic history-writing in all three languages — short punchy sentences, concrete specific details kept rather than smoothed into abstraction, and a dry closing line that reframes the facts as a joke. Model paragraph (`vysehrad-revival-1070`, the 1075 Langensalza / 1077 "Gebhard" aside): *"两人较劲用了不同的招——一个靠打仗立功，一个靠改名讨好皇帝——看来'想方设法气对方'才是这家人真正代代相传的东西。"* That's the target register for pre-modern content generally, not just this one event. Exception: modern-era atrocity/mass-death content (e.g. Lidice) stays solemn — same format, drop the jokes, not a Lidice-only rule. **Broader 20th-century pullback (confirmed 2026-08-24):** once content reaches the eras `brief-independence` (1918–1938), `nazi-nightmare` (1938–1945), and `cold-war-sorrow` (1946–1992) — see `data/historyEras.js` — default to a more restrained, measured voice generally, not just for individual atrocity-tagged events within them. Dry irony and understatement can still land (e.g. an era tagline noting Czechoslovakia's allies "hand it over to appease the neighbor next door"), but drop the punchy joke-closer structure that defines the earlier-era default, especially for anything touching occupation, violence, or repression directly. The material carries more sustained weight than earlier eras; the wit shouldn't be the default assumption that then gets card-by-card overridden.
- **Dash frequency (confirmed 2026-08-25):** em-dashes (`—`) had crept into overuse across all three languages, and the density itself makes sentences feel long and hard to read — pull back the frequency in new History Timeline prose, EN/CZ/ZH alike. Prefer a plain comma, a period and a new sentence, a colon where the aside is doing real explanatory work, or parentheses for a genuine aside/qualifier. **Not a ban** — the user confirmed explicitly ("也不是完全不能用破折号，但是要在不得不用的时候才用"): treat it as a last resort, reached for only when none of those alternatives actually works, not as one option among several to pick freely. This is a general house-style tightening, not specific to one language (compare [[feedback_natural_sentence_style]], which flagged the same tic as a ZH-specific "AI tell" — that observation still stands, but the fix now applies everywhere).
- **Shorter paragraphs** (confirmed 2026-10-07, after the user split `two-kings-1438`'s opening paragraph twice and asked for clearer paragraphing from now on): in `summary`, give each idea or story step its own paragraph (the problem, the cause, the decision, the action) instead of packing several beats into one block. A paragraph of more than about 4–5 sentences, or one that changes topic partway, should usually be split. Use the same breaks in EN/CZ/ZH.
- **Avoid the "this timeline" self-reference** (confirmed 2026-08-30, user said it reads badly and explicitly dislikes it): don't write card copy that breaks the fourth wall to talk about "this timeline" as a narrating entity — "this timeline already covered...", "这条时间线已经讲过...", "tahle časová osa už..." — even though this exact device had been in near-constant use across the whole file before this date (roughly 70–80 occurrences at the time it was flagged). Prefer a [[link:slug]] cross-reference (see below) when the callback target has its own card, or just rephrase the callback to an in-story actor instead of the meta-narrator — e.g. "Charles's own court had already worn out the story it was so eager to spread" rather than "this timeline has already told the story Charles's own court was so eager to spread." This is confirmed as a going-forward default for all new/edited copy; the large stock of already-shipped cards using the old device was NOT swept retroactively as part of this fix — only ask about a full retroactive pass if the user raises it, don't assume it's wanted.
- **Vary the forward-hook closer** (confirmed 2026-08-25): a card that deliberately doesn't finish its own story (leaving the actual next event for its own card) needs some closing line gesturing at what's coming, but "接下来发生的事，是另一个故事了" ("What came next is its own story") had become a reflexive default across the Rise-of-a-Kingdom arc — used on `crowned-twice-1307`, `seven-kings-then-none-1306`, `thoroughly-incompetent-king-1307`, `the-fleeing-princess-1310`, and others in a row. Don't lean on this one stock phrase every time. Vary the construction: name what's coming without narrating it ("what he did with it is its own story"), end on an image or irony instead of a meta-statement about "the story," pose it as an open question, or just stop cold on the last concrete fact and trust the reader to feel the cliffhanger without a signposting sentence at all. The underlying job (close this card without spoiling the next one) stays the same; the sentence doing that job shouldn't read identically card after card.

  - **Sticky-positioning gotcha:** `.guide-page` (shared by `GuidePage`, `TreasureHuntPage`, and `HistoryPage`) sets `overflow-y: auto` in `pixelart.css`. `#root` only has `min-height` (not `height`), so `.guide-page` never actually needs to scroll internally in practice — the real scrolling always happens at the window level — but the `overflow-y: auto` declaration alone still makes it a CSS "scroll container", which silently breaks `position: sticky` on any descendant (sticky computes against the nearest scroll container, and `.guide-page`'s own `scrollTop` never moves). `history.css` overrides it back to `overflow-y: visible`, scoped to `.history-page` only — don't remove that override, and don't add `position: sticky` inside `.guide-page` on another page without adding the same kind of scoped override.

Only visible on mobile (below the `820px` breakpoint), where `.history-layout` stacks to a column and the full-width sidebar and full-width feed share the same horizontal space — on desktop they sit side by side and never visually overlap, so this is easy to break without noticing on a desktop-only check. Don't remove the z-index.
  - Related landmarks render inside the shared `.location-grid` class from `pixelart.css` (so column widths/gaps match Explore's grid), but each grid item is a `.history-landmark-item` wrapper (flex column: `LocationCard`, then its relation caption right underneath) — not a bare card — see `HistoryEventSection`. An earlier version kept cards as direct, unwrapped grid children specifically to preserve CSS Grid's default `align-items: stretch` (uniform card height per row), with captions rendered in a wholly separate second grid below; replaced (2026-08) because captions needed to sit directly under their own card, not just visually approximated via matching column math. Cards in a row still get equal heights (2026-10-22, user request): each wrapper is a two-row subgrid (`grid-row: span 2; grid-template-rows: subgrid`, under `@supports`), so the card row stretches to the tallest card and the captions start on one line; the flex column is only the fallback. Rows are balanced and short rows centred (same day): each card spans two of six tracks (four below 722px container width), `landmarkStarts` in `HistoryEventSection.jsx` gives 4 → 2+2 and 7 → 3+2+2 on desktop, and the "See it for yourself" heading is centred too (user's preference). Phones (≤600px) keep both left-aligned, as before.
  - **Load performance (2026-09-25):** the feed renders all ~220 events at once, so four things keep it fast; don't remove them casually. (1) `GET /api/history?lang=<en|cz|zh>`: the client sends its language and the controller collapses every `{ en, cz, zh }` object to `{ [lang]: value || en }` (~1 MB → ~0.35 MB compressed), so switching language refetches. Without `lang` all languages come back. Landmarks carry only LocationCard's fields. (2) The controller caches the assembled payload in memory per language, checked on every request against the count plus newest `updatedAt` of `historyevents` and `locations`. A Mongoose `updateOne` sync (which bumps `updatedAt`) or a reseed shows up on the next request; a raw-driver write that doesn't touch `updatedAt` would not. (3) `.history-detail-panel` has `content-visibility: auto`, so off-screen panels skip layout. Before this, every CJK web-font slice finishing its download relaid the entire ~700k-px feed (1–2 s each, ~12 s to first paint on ZH). Because far panels hold placeholder heights, `scrollToSlug` re-snaps to the target when the smooth scroll ends, and `LocationCard`'s label fit skips cards the browser isn't rendering (`checkVisibility`) and lets its ResizeObserver fit them later. (4) Event images are `loading="lazy"` with `width`/`height` from `src/utils/historyImageSizes.json`, generated by `scripts/generateHistoryImageSizes.mjs` (runs before `npm run dev`/`npm run build`, and on file changes in `public/history/` while dev is running), so lazy images don't shift sidebar jump targets.
  - **Reading progress (2026-09-25):** `/history` reopens at the event the reader was last on (the sidebar's active slug), scrolled to its start. Every reader gets a `localStorage` copy (`historyProgress`, `utils/historyProgress.js`); signed-in users also get a server copy on `User.historyProgress` (`GET`/`PUT /api/user/history-progress`), and on load the newer of the two wins, so progress follows a user across devices. Server saves are debounced 2 s while scrolling (3 s until 2026-11-04, shortened so a position held 2 s counts for Turning the Page) and flushed (fetch `keepalive`, `saveHistoryProgressOnExit` in `api.js`) when the page is hidden or the user navigates away. `HistoryPage` sets `history.scrollRestoration = 'manual'` while mounted, since the browser's own pixel-offset restore would land somewhere arbitrary on the async, placeholder-height feed. Nothing is saved until the restore has run, so the initial top-of-page highlight never overwrites a saved position.
  - `unlocked` is force-set to `true` when a landmark is passed to `LocationCard` here — History isn't a discovery/gamification context (the event text already names the place), so Explore's "???" mystery treatment never applies on this page, regardless of the requester's real check-in state.
  - Clicking a landmark card opens the real `LocationDetail` as an overlay on top of the History page itself (`HistoryPage` owns `openLandmarkSlug` state and renders `<LocationDetail>` directly, same pattern `RandomDrawPage` uses) — not a navigation to `/explore`.
  - Each event's `<h2>` title doubles as its Wikipedia link (new tab, no underline, only a hover color shift) when `wikipediaUrl` is set — replaced an earlier standalone "Wikipedia" text link below the summary (2026-08).
  - Sidebar era titles and left-border stripes are a flat `var(--gold)` everywhere, not the per-era `--era-accent` palette (`data/historyEras.js`'s `themeClass` → `.era-*` rules in `history.css`, which included a red and a purple) that used to color them. That per-era system is still defined in CSS but currently unread by anything — kept in case per-era theming comes back elsewhere, not dead code to delete casually.
  - **Chinese pixel-font gotcha:** title-level classes here (`.history-event__title`, `.history-sidebar__era-title`) use `font-family: 'Press Start 2P'`, a Latin-only font. Without a matching entry in `global.css`'s `html[data-lang="zh"] ...` override block, Chinese text in that class silently falls through to a generic `monospace` fallback — same declared `font-size`, but visibly smaller/thinner than the Latin pixel font renders, reading as "this heading has no presence." When adding a *new* class with this font-family that Chinese users will see, add it to that override block (font-family swap + a larger zh-specific `font-size`) in the same pass, not as an afterthought.
  - **Mobile horizontal-overflow gotcha (fixed 2026-08, worth understanding if it comes back):** `.history-layout`'s base rule sets `align-items: flex-start` — correct on desktop, where the layout is row-direction and it lets the sidebar and feed size their *heights* independently. The `@media (max-width: 820px)` block switches `.history-layout` to `flex-direction: column` but originally never touched `align-items` — so on mobile the cross axis becomes horizontal, and `flex-start` there means children shrink-to-fit their own content's preferred width instead of stretching to the container's 100%. `.history-feed` has no width of its own, so it was sizing itself to the widest thing inside it (in practice the 2-column `.location-grid` in related-landmark sections, wanting ~630–680px) and dragging the *entire page*, navbar included, into horizontal scroll — not just the History section, even though only History-specific content was the actual cause. Fixed by adding `align-items: stretch` inside that same mobile media query. A second, smaller contributor: CSS Grid/Flex items default to a content-based automatic minimum width that only zeroes out for boxes with their *own* non-visible `overflow` — `.loc-card` has `overflow: hidden`, but the `.history-landmark-item` wrapper around it (the actual `.location-grid` item now) didn't, so long location names could still inflate its track. Fixed with `min-width: 0` on `.history-landmark-item`. If mobile overflow ever resurfaces on this page, check both of these first — verify live with `document.body.scrollWidth` vs `window.innerWidth` plus a `getBoundingClientRect().right` sweep for offending elements (screenshots alone will mislead you: a page that's horizontally scrolled looks like content is "cut off on the left," which reads as a completely different bug from what it actually is).

### Content gotchas and lessons

- **Vratislav vs Vladislav** — two different men a century apart: Vratislav II (r. 1061–92, first king 1085) vs Vladislaus II (r. 1140–73, second "borrowed crown" 1158). Established ZH: **弗拉季斯拉夫** = Vratislav, **弗拉迪斯拉夫** = Vladislav (季 vs 迪), checked against zh.wikipedia. Don't let a casually-typed draft suggestion "fix" this. No Bohemian Vratislav was ever crowned king except Vratislav II (`romansky-most-vysehrad` once said "Vratislav I"; fixed).
- **Verify large edits**: one large Edit silently turned straight quotes into curly quotes across a whole block (caught only by `node --check`). Re-run `node --check` after *every* large edit to `seedHistoryEvents.js`, not just before the DB sync.
- **Direct-DB sync writes**: a `troskovice` sync reported `modifiedCount: 1` and read back fine, then silently reverted (likely racing the un-guarded `seedLocations.js` upsert on import plus non-majority write concern). Fixed by guarding both seed scripts' upsert loops behind an `import.meta.url` entry-point check and by using `{ writeConcern: { w: 'majority', j: true } }`. For anything that matters, re-verify from a separate connection after a delay before saying it's live ([[feedback_db_sync_write_durability]]).
- **Live-DB drift** (standing gotcha): `hrad-trosky` is live as `legend`/100 XP while the seed says `epic`/50; `troskovice` is live `common`/10 while the seed says `rare`/20. Unreconciled, root cause unknown — only `description` was synced.
- **`referenceMaps` reuse**: its UI label was genericized to "More on this:" / "延伸资料：" / "Více k tomuto tématu:" (`history.referenceMapsLabel`), which also changed the 5 map-only cards. First non-map use: the 1955 film *Jan Žižka* clip on `the-first-defenestration-1419`.
- **Background-card feature** touches `HistoryEventSection.jsx`, `HistorySidebar.jsx`, `HistoryPage.jsx`, `history.css` and i18n keys `history.backgroundLabel`/`collapseCard`/`expandCard`; verify frontend changes with a full `vite build`, not just `node --check`.
- **`[[link:…]]` and `[[b]]` don't nest**: `INLINE_MARKUP_RE` in `HistoryEventSection.jsx` matches them in one flat pass, so a link inside a `[[b]]…[[/b]]` span renders as literal bracket text. Keep links outside bold sentences (caught before shipping on `undefeated-until-the-plague-1424`).
- **Inline `[[link:…]]` renders as `<span role="button" tabIndex={0}>`, not `<button>`** (a `<button>` is an atomic box and won't wrap mid-phrase). Link color: default `var(--text-primary)`, gold only on `:hover`; the underline marks it as a link.

### Illustrations

The illustration production rules (prompt template, standard frame, `fillMargins.py`, caption and battle/banner rules) and the locked character designs live in `docs/illustrations.md`. **Read it before writing any illustration prompt**, and add each newly accepted character design there, not here.

**Style rules, use in every prompt (user's call, 2026-11-01, learned over era 15's first three cards):**
- **Default style for real events** (battles, sieges, scenes with real people): *"realistic proportions and serious faces, the atmosphere and gravity of an 18th-century battle painting, painterly and highly detailed; NOT cartoonish, NOT comic, NOT caricature, NOT chibi"*. The user prefers this painterly look over the old toy-soldier pixel art (rejected on Mollwitz as "not majestic") and over a Hogarth-style comic take on a real event (rejected on the 1741 siege as too cartoonish for a serious card).
- **Comic/satirical style only for allegories** (a symbolic scene that never happened, like the coalition cake in `fire-on-every-side-1741`): *"in the spirit of an 18th-century satirical painting by Hogarth: exaggerated, theatrical expressions and body language, playful caricature… still painterly and well drawn, NOT a cartoon, NOT chibi"*, with one comic action per figure tied to the card's text. Plain realism there was rejected as "no humour".
- **Light**: always *"CLEAR, BRIGHT and readable, NOT dark, NOT muddy, NOT brown"*; for night scenes a bright full moon with cold silvery-blue light and small warm accents (torches, cannon flashes). Night plus "18th-century painting" otherwise turns into dark brown sludge.
- **Grand scenes**: put a CAMERA AND SCALE block first: *"a HIGH, FAR bird's-eye panorama… the city/landscape dominates, all soldiers are SMALL figures, no close-ups"*, and give each part of the scene its compass position. Keep it to about four groups of elements; eight or nine (city, river, bridge, ladders, waders, army, leader, cannonballs, a side scene) gave a cluttered collage twice. Cut side jokes before cutting the main action.
- **Format line**: start with *"IMAGE FORMAT: a wide 16:9 landscape image (for example 1024 x 576), NOT 3:2, NOT 4:3"*; one generation came back 1024×687 and could not be cropped without cutting the painted frame.
- **Frame and plaque**: add *"NOT a wooden frame, NOT a gilded picture frame, NOT a scroll"* (one try drew a gilt picture frame), and for the caption *"bold UPRIGHT serif… NOT italic, with NO quotation marks or apostrophes… Do not shorten or cut the caption"* (one try dropped three of four words, others added quotes or italics).
- **Flags**: name each army's flags, their colours/emblem as an icon, and where they stand; ask for them *"LARGE, fully unfurled… clearly lit"* when they carry the meaning. Saxony needs *"horizontal stripes alternating BLACK and GOLD crossed by ONE narrow GREEN diagonal band of small leaves; NO red, NO cross"* (twice drawn as a red saltire otherwise).
- **No style reference images**: uploading an accepted image as a style reference gave worse results than a full written prompt; always write the complete prompt and start a fresh generation.
